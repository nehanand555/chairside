# Google sign-in setup

Google sign-in uses Supabase Auth. It needs no Twilio account or SMS sending. Google OAuth configuration is separate from Google Maps/Places billing and API keys. The app uses the existing Supabase project, data, RLS and booking rules.

## 1. Deploy the code and new database migration

Merge the Google login change into `main`. In GitHub Actions run **Deploy configured services**, branch `main`, target `backend`, environment `staging`. This applies the new `202610180001_google_sign_in.sql` migration and deploys the updated functions. Never modify already-applied migrations or reset the database to switch login.

## 2. Create a Google OAuth client

1. Open https://console.cloud.google.com/ and select or create a project named **Chairside**. Google sign-in alone does not require enabling paid Maps APIs.
2. Open **Google Auth Platform**. Complete **Branding** with app name Chairside, your support email and developer contact email. Use your own contact details.
3. Set **Audience** to **External**. While the app is in Testing, add your own and your partner's Google account addresses as test users.
4. Under **Data Access**, request only `openid`, `https://www.googleapis.com/auth/userinfo.email` and `https://www.googleapis.com/auth/userinfo.profile`. These identify the account; they do not request Gmail, Drive or contacts access.
5. Under **Clients**, create an OAuth client of type **Web application**, named **Chairside Supabase**. This backend OAuth client handles browser-based login for web, Android and iOS.
6. Add your hosted app's exact HTTPS origin under **Authorized JavaScript origins** once hosting exists. For local web testing, also add `http://localhost:3000`.
7. Under **Authorized redirect URIs**, add the callback shown in Supabase's Google provider settings: `https://YOUR_PROJECT_REF.supabase.co/auth/v1/callback`. Copy it from your own project; do not enter the app's custom URL scheme here.
8. Create the client. Copy the client ID and client secret directly to Supabase. Never put the client secret in GitHub variables, Flutter, screenshots or chat.

## 3. Enable Google in Supabase

1. Open your project → **Authentication → Sign In / Providers → Google**.
2. Enable Google and enter the Google **Client ID** and **Client Secret**. Save.
3. In **Authentication → URL Configuration**, set **Site URL** to the deployed app's HTTPS root URL. Under **Redirect URLs**, allow that exact root URL, with trailing slash, and `nz.chairside.chairside://login-callback/`. For local web testing add `http://localhost:3000/`. Avoid wildcard production callbacks.
4. Leave the Phone provider disabled if SMS is not configured. App login uses Google; database support for older verified-phone accounts does not enable SMS by itself.
5. Ensure app-authenticator TOTP enrollment and verification are enabled. These protect business/admin functions independently of Google sign-in.

The app uses PKCE and the Supabase Flutter SDK to exchange the returned code and restore the session. Android intent filters and iOS URL types are generated by `tool/bootstrap.py`; rebuild native apps after this change. If you change the permanent bundle ID/callback scheme, update both platform generation, `SupabaseBackend.signInWithGoogle`, and Supabase's redirect allowlist together.

## 4. Build and test

Deploy the web app through **Deploy configured services → web**, or run the existing configured Flutter web build locally on port 3000. No Google client secret belongs in `build-config.json`. The client uses only the existing `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`.

Accept the terms and choose **Continue with Google**. After returning, save your name in Account, then book a real test appointment. Check My visits for status changes. Google accounts without verified phone numbers should see no Booking texts switch, and booking must not require a phone number. Business owners must still enroll an authenticator before applying. Test cancellation/retry of Google login, a fresh browser, sign-out, return from the mobile browser, account deletion and blocked-user rejection against hosted Supabase.

Google's Testing audience limits access to listed test users. Complete Google publishing/brand requirements before inviting general customers. Before App Store submission, assess Apple's current login-services rules and supply an equivalent privacy-preserving sign-in option where required; Google login alone is not an assertion of App Store approval.
