# Operating Chairside

- Monitor GitHub Product checks, Supabase Auth/Edge Function errors, Cron history, `net._http_response`, Stripe event deliveries/refund failures, and Twilio message status. Admin health shows failed/overdue SMS and pending refunds. Investigate provider logs before resending an ambiguous SMS; the worker deliberately avoids automatic duplicate sends after an interrupted request.
- Enable managed database backups appropriate to your plan and test a restore into staging. Back up storage objects separately: a database backup does not include their image bytes. Keep a copy of SQL migration history. Do not edit applied migrations in a live project; add new ones.
- Use MFA on provider/admin accounts, GitHub, Supabase, Google, Twilio, Stripe and Cloudflare. Restrict deployment tokens, client map keys and API quotas. Rotate leaked credentials. The publishable Supabase key alone does not grant data access; review RLS after schema changes.
- Operators can pause new queue entries, schedule breaks, cancel upcoming visits and issue full refunds. They cannot complete an unstarted visit or start a second customer on the same chair. A delayed queue may no longer fit before closing: the business must contact/cancel remaining visits; it must not promise estimates as exact arrival times.
- Cancellation before service and no-shows request full refunds in this release. Refunds complete asynchronously. Do not mark a visit refunded manually in the client. Stripe is authoritative for refunds, disputes and financial reconciliation. Refunds initiated directly in Stripe must be full refunds to be reflected automatically; partial refunds are handled in Stripe and require manual reconciliation until partial-refund support is added.
- SMS consent is separate from marketing consent. Preference changes update existing visit contacts. Do not use booking contacts for promotions. Twilio opt-out handling may block later messages even if app consent remains enabled; review consent/provider status when supporting a user.
- Account deletion requires recent sign-in, no active visits/pending refunds, and a closed owned business. Customer contact records are removed and visit names anonymised; Auth is soft-deleted to preserve financial references. Establish a lawful business/financial retention schedule and a support process for deletion/access requests before launch. Closed-business legal/financial records are not automatically purged.
- Recovery of a lost business authenticator requires a verified support process in Supabase administration; there is no public bypass endpoint. Record and audit administrative recovery actions. Maintain at least two securely controlled platform admins.
- RLS/booking tests run on PostgreSQL 17 using minimal Supabase Auth/Storage contracts. They are not an end-to-end certification of the hosted Supabase service, a native-device test, a penetration test or a payment/SMS test. Re-run managed-service smoke tests in staging when those integrations change.

Known constraints: one owner account, no employee-role invitations, common hours for all chairs, no overnight/repeating exceptions, maximum one active visit per customer, 90-day appointment window, no automatic no-show penalties, full-refund-only UI, SMS rather than native push. These are explicit product rules for the first operating release.
